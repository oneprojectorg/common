# Drop unbounded proposal-id materialization in phase scoping

Asana: https://app.asana.com/0/1213315744811204/1215883488977187

## Problem

`getProposalsForPhase.ts` resolves phase membership by issuing three
`SELECT id FROM proposals/decision_transition_proposals WHERE ...` queries
with no `LIMIT`, then shipping the materialized UUIDs back to Postgres as
`inArray(proposals.id, [...])` on every page of `listProposals`. A 10k-proposal
process turns into a multi-KB IN list per request — including page 2.
`listProposals` does the same trick with `proposalCategories` for `categoryId`.

## Approach

Push phase scoping into the proposals SELECT as a correlated predicate that
combines, ORed:
- `EXISTS` over `decision_transition_proposals` for the inbound transition.
- A `createdAt` window predicate from `inboundAt`/`outboundAt` resolved once.

The phase window is still resolved up front via `stateTransitionHistory`
(bounded by transitions per instance, not by proposals). After that, no IDs
are materialized in `listProposals` — the predicate lands in the proposals
WHERE directly. Same idea for the category lookup → `EXISTS` against
`proposalCategories`.

Other consumers of `getProposalIdsForPhase` (advancePhase, processResults,
listSelectionCandidates, etc.) still legitimately need ID arrays, so the
function keeps its signature but collapses internally from 3 helper queries
to one `SELECT id FROM proposals WHERE <phase predicate>`.

## Files

- `packages/common/src/services/decision/getProposalsForPhase.ts`
  - Add `resolvePhaseScope` + `buildPhaseScopeSql` (exported).
  - Rewrite `getProposalIdsForPhase`, `getPhaseProposalAndDraftIds`,
    `getProposalsForPhase` on top of them.
  - Drop `attachmentIdsFor`, `getIdsCreatedDuringWindow`,
    `getActiveIdsByPredicate`, `getActiveNonDraftIdsForInstance`.
- `packages/common/src/services/decision/listProposals.ts`
  - Replace phase id `inArray` with the SQL phase scope predicate.
  - Replace `categoryProposalIds` materialization with `EXISTS` against
    `proposalCategories` (mirrors `listAllProposals.ts`).
- New test cases against `listProposals` + `getProposalsForPhase` that pin
  the membership semantics so the refactor can't regress attachment vs
  window vs draft scoping.

## Edge cases

- Legacy instance: no phase scoping (scope `noPhase` → returns
  `status != DRAFT` only).
- Phase never entered (unreached): scope returns `false` predicate; caller
  short-circuits to empty result.
- Initial phase (no inbound transition): no `EXISTS` branch; window relies
  on `outboundAt` only.
- Current phase (no outbound transition): no upper-bound window predicate.
- Drafts: `[inboundAt, outboundAt)` window only (no `EXISTS` branch), plus
  access predicate via `profileUsers` subquery (already in SQL).
- Soft-deleted proposals: `isNull(deletedAt)` still applied at the outer
  query — the phase predicate must not include it.

## Out of scope

- Other callers of `getProposalIdsForPhase` (advancePhase, processResults,
  listSelectionCandidates, listProposalSubmitters,
  listProposalsWithReviewAggregates, submitManualSelection,
  getPhaseReviewProgress) — they still need ID arrays for their own logic;
  they benefit from the collapsed-internals query but are not refactored
  to predicate-style here.
