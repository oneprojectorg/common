# Rate-limit: move from in-memory Map to Redis sliding window + safe XFF

Asana: https://app.asana.com/0/$ASANA_PROJECT_ID/1215883488980510

## Problem

`services/api/src/lib/rateLimited.ts` is broken in three independent ways:

1. **Memory leak.** The module-scoped `Map<string, …>` keyed by `${ip}-${reqUrl}` only ever grows — entries are never deleted. Under cursor variation the key cardinality explodes.
2. **Per-Node-instance state.** With N replicas, every limit is multiplied by N. The login OTP cap (3 req / 10 s) is the worst offender because attackers can fan a credential-stuffing burst across replicas.
3. **Spoofable IP.** `ctx.ip = req.headers.get('X-Forwarded-For')` is the raw header. An attacker prepends a random UUID per request and gets a fresh rate-limit bucket each time.

## Approach

- Replace `services/api/src/lib/rateLimited.ts` with a Redis-backed sliding-window log (sorted-set: ZADD score=now, ZREMRANGEBYSCORE outside the window, ZCARD to count, PEXPIRE to keep the key bounded). Atomic via `MULTI`.
- Add a bounded LRU fallback (`lru-cache`) that kicks in when Redis is absent or the round-trip times out, so the limiter degrades gracefully instead of fail-opening to the existing leak.
- Place the new primitive in `@op/cache` (`services/cache/rateLimit.ts`) so it sits next to the other Redis state and gets unit-tested under the same fast vitest config (no Supabase dependency).
- Key the limiter on `(authUserId ?? trimmedClientIp, procedurePath)`. To make `ctx.user?.id` available to `withRateLimited`, reorder the procedure factories so `withResolvedUser` runs *before* `withRateLimited`. `getCachedAuthUser` is `WeakMap`-cached per `ctx`, so the downstream `withConfirmedUser` / `withNetworkAuthenticatedUser` still pay zero extra cost.
- Add a safe IP parser in `@op/core` (`parseClientIp.ts`) that prefers `x-real-ip` (Vercel sets this to the actual client) and falls back to the *rightmost* entry of `X-Forwarded-For` — everything to the left can be spoofed by the client.
- Use the parser at context creation in `trpcFactory.ts` so `ctx.ip` is always the trimmed client IP, never the raw header.

## Files

- `services/cache/rateLimit.ts` (new) — `consumeSlidingWindow({ key, windowMs, maxRequests })`.
- `services/cache/rateLimit.test.ts` (new) — Redis hit/miss/timeout, LRU fallback, window expiry, multi-key isolation.
- `services/cache/index.ts` — re-export.
- `packages/core/src/parseClientIp.ts` (new) — `parseClientIp(headers)`.
- `packages/core/src/parseClientIp.test.ts` (new) — preference order, trimming, missing headers, rightmost XFF.
- `packages/core/src/index.ts` — re-export.
- `services/api/src/middlewares/withRateLimited.ts` — async, key by `ctx.user?.id ?? ctx.ip` + `ctx.reqUrl`.
- `services/api/src/trpcFactory.ts` — call `parseClientIp(req.headers)`; reorder `withResolvedUser` before `withRateLimited` in all four procedure factories.
- `services/api/src/lib/rateLimited.ts` — delete (replaced by `@op/cache`).
- `services/api/package.json` — depend on `@op/cache` (already does); drop nothing else.

## Edge cases

- Anonymous + no IP: throw `UnauthorizedError` exactly as today — we refuse to limit on a missing identity.
- Login route (`commonProcedure`): no `withResolvedUser` ever runs, so `ctx.user` is `undefined` and we fall back to the trimmed IP. The 3 req / 10 s cap is preserved.
- Server-side calls (`ctx.isServerSideCall`) and E2E (`process.env.E2E`, `process.env.TEMP_DISABLE_RATE_LIMITING`): bypass unchanged.
- Redis down: ZSET ops time out → fall through to the bounded LRU. LRU has its own sliding-window log (array of timestamps per key) with a hard entry cap so it can't leak the way the existing Map does.
- Vercel double-`x-forwarded-for`: still rightmost wins, which is the proxy adjacent to us — the trusted boundary.

## Out of scope

- Replacing the rate limit semantics for any specific procedure.
- Per-tenant or per-route override config — the existing `{ windowSize, maxRequests }` shape is preserved.
- Logging/metrics for rate-limit hits (could be a follow-up).
- A configurable trusted-proxy CIDR list — `x-real-ip` (Vercel) covers the platform we deploy on; the rightmost-XFF fallback is safe under standard reverse-proxy behavior.
