# Realtime: add timeout, retry, and failure metrics to broadcast publish

Asana: https://app.asana.com/0/1213315744811204/1215899057912983

## Problem

Realtime broadcast publishing is best-effort and silently so:

- `RealtimeClient.publish` passes no `signal`, so a hung Supabase connection
  hangs for undici's default (~300 s) rather than anything we chose. There is
  no retry for a transient 5xx either.
- The moderation webhook `await`s `Promise.all(channels.map(publish))` **on the
  response path**, and its route declares no `maxDuration`. A hang therefore
  stalls the webhook until the function is killed → 5xx → the provider retries
  → `recordModerationVerdict` is idempotent and returns `noop` → the
  invalidation guard is skipped → **the invalidation is permanently lost** while
  the flag is correct in the DB.
- Failures go to `console.error` with no metric and no structured log, so an
  invalidation outage is invisible.
- One failing channel discards the whole `Promise.all`, taking the other
  channels' invalidations with it.

## Approach

Fix resilience and observability; leave the transport shape alone (one request
per channel).

- `RealtimeClient.publish` wraps its `fetch` in `withRetry({ retries: 1 })`
  (`packages/core/src/retry.ts`) with a **fresh** `AbortSignal.timeout(3000)`
  per attempt, and drains the response body on success so the retry can't
  orphan a socket per attempt.
  - Retry on 5xx and network errors/timeouts. Not on 501/505 (never heal).
  - **Not** on 429: the 0–200 ms jittered backoff lands inside the same
    rate-limit window, so retrying only adds load to a backend that just asked
    us to slow down.
  - Echo Supabase's own error text (truncated to 200 chars) into the thrown
    error, so a non-retryable 4xx is diagnosable.
- `RealtimeService.publishMany(channels, message)` dedupes, then publishes each
  channel concurrently via `Promise.allSettled`, so **one failing channel no
  longer discards the rest**. Failures are swallowed (publish happens after the
  mutation commits), counted on the `realtime.publish.failures` OTel counter,
  and logged via `@op/logging` with the *failing* channel names (capped at 10).
- The counter counts failed **channels**, so it needs no attributes — fan-out
  size is data-driven and unbounded and would otherwise be one time series per
  distinct count.
- `handleModerationWebhookRequest` moves the channel lookup + publish into
  `waitUntil` from `@vercel/functions`, off the response path entirely. The
  whole block is try/caught so a throw from the channel lookup can't reject the
  backgrounded promise.

## Batching was considered and dropped

An earlier revision of this branch collapsed the fan-out into one multi-topic
`messages` array, chunked per request. It was removed because:

- `dev` already fires the per-channel publishes in parallel, so batching was a
  request-*count* win, not a latency win — and the tRPC path is backgrounded in
  `waitUntil`, so nobody waits on it either way.
- Each message still counts as one Supabase broadcast event, so it bought no
  event-quota headroom.
- There is no failure metric in production yet, so there was no baseline
  showing the current behavior costs anything.
- It introduced the only new failure mode in the change: Supabase rejects a
  batch of 92+ messages with a 429 (`"Too many messages to broadcast, please
  reduce the batch size"`; measured locally — 91 accepted, 92 not). Because 429
  is non-retryable and publish errors are swallowed, an oversized fan-out lost
  *every* invalidation silently. The ceiling is per request, not aggregate.

Revisit if the new counter shows request volume actually matters.

## Files

- `services/realtime/src/server/client.ts` — timeout, retry, body drain,
  server-error detail.
- `services/realtime/src/server/service.ts` — `publishMany` per-channel
  `Promise.allSettled` fan-out, dedupe, OTel counter, `@op/logging` (replaces
  `console.error`).
- `services/realtime/package.json` — depends on `@op/core` (`withRetry`) and
  `@op/logging`.
- `services/api/src/middlewares/withChannelMeta.ts` — one
  `realtime.publishMany(channels, ...)` call instead of a per-channel loop.
- `services/api/src/moderation/handleModerationWebhookRequest.ts` — publish
  moved into `waitUntil`.
- `services/realtime/tsconfig.json` — extends `base.json` rather than
  `nextjs.json`, which had been masking `noUncheckedIndexedAccess`.
- Tests: `client.test.ts` (retry/timeout/status policy), `service.test.ts`
  (dedupe, swallow, counter, log), `publish.integration.test.ts` (end-to-end
  delivery against local Supabase, including a 120-channel fan-out).

## Edge cases

- Empty channel list → no-op (no fetch, no log, no metric).
- Duplicate channel names within a registration → deduped before send.
- Missing `NEXT_PUBLIC_SUPABASE_URL` / `SUPABASE_SERVICE_ROLE` → caught
  separately from per-channel failures (it is a whole-service failure), still
  swallowed, counted once per channel.
- Retry amplification: a Supabase brownout now costs up to 2N requests where it
  previously cost N. Bounded by `retries: 1` and a typical fan-out of 5–10, so
  ~20 requests worst case.
- The tRPC call site is already inside `waitUntil`, so the retry + 3 s timeout
  adds at most ~6 s of *background* work per mutation.
- Backwards compat: `realtime.publish(channel, msg)` keeps working (delegates
  to `publishMany`).

## Out of scope

- Aggregating channels across multiple `registerMutationChannels` calls in one
  procedure. The middleware publishes at registration time, so a `next()` that
  later throws still publishes; changing that timing is a separate behavior
  change.
- The client-side `mutationId` dedupe in `QueryInvalidationSubscriber.tsx`,
  which can drop sibling-channel invalidations. Pre-existing; needs its own
  ticket.
- Changing the message envelope (`event: 'invalidation'`, payload schema).
