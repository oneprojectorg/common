# Realtime: batch broadcast publishes with publishMany + retry/timeout

Asana: https://app.asana.com/0/1213315744811204/1215899057912983

## Problem

In `withChannelMeta`, every mutation channel is published with its own
`fetch` POST (a single-element `messages: [{...}]` body). Fan-out for
`createLink`, `channelsForPost`, `collections/delete` is 5–10+ channels per
mutation, so we make 5–10+ HTTP round-trips when one would do. Errors
are swallowed by `console.error`, with no metric or structured log, and
no timeout/retry on transient Supabase Realtime failures.

## Approach

- Add `RealtimeClient.publishMany({ messages, signal? })`. Posts one body
  with the full `messages` array (multi-topic batch — the Supabase
  Realtime REST endpoint accepts it).
- Wrap the `fetch` in `withRetry({ retries: 1 })` with a fresh
  `AbortSignal.timeout(3000)` per attempt. Retry only on 429 / 5xx
  (network errors retry automatically by throwing). 4xx surface
  immediately — they will not heal on retry.
- Move single-channel `publish` to delegate to `publishMany` so there is
  one transport path.
- Add `RealtimeService.publishMany(channels, message)` that:
  - dedupes channel names,
  - calls `client.publishMany`,
  - swallows the error (publish is best-effort, same as today),
  - replaces `console.error` with `logger.error('[Realtime] publishMany failed', {...})`,
  - bumps an OTel counter via `@op/logging` so realtime failures are
    visible in metrics.
- Switch the per-channel loop in `withChannelMeta.registerMutationChannels`
  to one `realtime.publishMany(channels, { mutationId })` call.
- Switch the `Promise.all(channels.map(...))` in
  `handleModerationWebhookRequest` to the same single call.

## Files

- `services/realtime/src/server/client.ts` — add `publishMany`, route
  `publish` through it, add retry + timeout helper.
- `services/realtime/src/server/service.ts` — add `publishMany`, dedupe,
  swap `console.error` for `@op/logging`, add counter.
- `services/realtime/package.json` — depend on `@op/core` (for
  `withRetry`) and `@op/logging`.
- `services/api/src/middlewares/withChannelMeta.ts` — single batched call.
- `services/api/src/moderation/handleModerationWebhookRequest.ts` — single
  batched call.
- New: `services/realtime/src/server/client.test.ts` — body shape,
  retry on 429/5xx, no-retry on 4xx, timeout abort.

## Edge cases

- Empty channel list → no-op (no fetch, no log, no metric).
- Duplicate channel names from a single registration → dedupe before send
  (saves Supabase work; clients only care about the first invalidation).
- A single `fetch` 5xx after the retry → we swallow the throw, log once,
  bump the counter. The mutation has already committed; this matches the
  current "best effort" contract.
- The tRPC call site (`withChannelMeta`) is wrapped in `waitUntil` already
  (Vercel), so the retry + 3 s timeout adds at most ~6 s of *background*
  work per mutation — well inside `waitUntil`'s budget.
- The moderation-webhook call site is **not** in `waitUntil`; it is awaited
  on the response path, and `apps/api/.../webhooks/route.ts` declares no
  `maxDuration`. Worst case adds ~6.2 s to the webhook response. This is
  still strictly bounded where the previous `Promise.all` had no timeout at
  all, but it is slower in the degraded-but-alive case.
- Backwards compat: callers using `realtime.publish(channel, msg)` keep
  working (it delegates to `publishMany`).

## Out of scope

- Aggregating channels across multiple `registerMutationChannels` calls
  in one procedure into a single batch. Today the middleware fires the
  publish at registration time, which means a `next()` that later throws
  still publishes. Changing that timing is a separate behavior change.
- Changing message envelope (`event: 'invalidation'`, payload schema).
- Removing the single-channel `publish` surface from the service API.
