# Moderation webhook: persist payload then enqueue; verdict applied in workflow

## Problem
The webhook handler does the full verdict pipeline (SELECT FOR UPDATE
transaction, flag-store writes, realtime publish, Inngest emit for the
flagged-content email) before returning 200 to the vendor. Lasso/Checkstep/Hive
clients time out around 10 s and retry aggressively, producing duplicate
deliveries that re-do the locked work. Lasso also batches multiple actions per
delivery, so each batch multiplies the in-handler latency.

## Approach
- Add a `moderation_webhook_inbox` table — one row per delivery, unique on
  `(provider, deliveryId)` where `deliveryId = sha256(rawBody)`. Persists the
  raw body, headers, and metadata; tracks `processedAt` for observability.
- Webhook route becomes a thin shell: shared-secret check → provider configured
  check → vendor signature verify → insert inbox (skip on conflict) → emit a
  single Inngest `moderation/webhook-received` event → 200. No parsing, no flag
  writes, no realtime publish, no per-verdict emit in the route.
- Move parsing into a workflow: `dispatchModerationWebhookDelivery` reads the
  inbox row, parses it via the provider adapter, fans out one
  `moderation/verdict-received` event per verdict (carrying the full
  `ModerationVerdict`), and stamps the inbox row processed.
- Move application into a second workflow: `applyModerationVerdict` triggers on
  `moderation/verdict-received` with `concurrency: { key: 'event.data.itemId' }`,
  calls `recordModerationVerdict`, then publishes the realtime invalidation it
  used to do inline.

## Edge cases
- Vendor redelivery (the bug we're fixing): inbox unique constraint dedupes; we
  still 200 the redelivery so the vendor stops retrying, but we do not enqueue
  a second event.
- Lasso batches: the dispatch workflow fans out N verdict events from one inbox
  row.
- Stale or unparseable bodies: workflow logs and marks the row processed with a
  failure status; the vendor already got 200.
- Provider not configured / sig invalid: same status codes as today (503/401),
  no inbox row written.
- `concurrency.key = event.data.itemId` collapses concurrent verdicts for the
  same item, eliminating the SELECT FOR UPDATE contention path entirely.

## Out of scope
- Inbox retention/cleanup (track separately).
- Reprocessing UI / admin tooling.
- Changing the public realtime channel set.
